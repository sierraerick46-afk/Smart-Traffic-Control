# Smart Traffic Light Control · Chía

Machine learning project developed with the six phases of **CRISP-ML**. It forecasts the hourly traffic of four
intersections of Chía (Cundinamarca), groups the hours of the week into off-peak, moderate and peak, and uses the
forecast in a simulator where a DQN agent decides when to change the green light. Everything is documented inside a
Flask application.

| | |
|---|---|
| Learning task (main model) | Supervised regression: vehicles per hour by date, hour and intersection |
| Selected model | Gradient Boosting (HistGradientBoostingRegressor) |
| Independent test (May – Jun 2017) | see `artifacts/report.json` → `final.test` (R² ≈ 0.90, MAE ≈ 5.6 veh/h) |
| Supporting models | K-Means (k = 3) for the type of moment · DQN agent (PyTorch) for the signal |

## Reproduce the results

```bash
python train.py     # about 4 minutes on a laptop
python monitor.py   # about 10 seconds
```

`train.py` does, in order:

1. Loads and cleans `data/raw/traffic.csv` (invalid dates, negative counts and duplicates).
2. Splits the data **by time**: train Nov 2015 – Feb 2017, validation Mar – Apr 2017, test May – Jun 2017.
3. Fits the preprocessing **only on training data** (K-Means groups, outlier caps at the 99.5th percentile, scalers).
4. Tunes five models (seasonal mean, Ridge, Random Forest, Gradient Boosting, MLP) with 5-fold `TimeSeriesSplit`
   on the training partition; every configuration is written to `artifacts/experiments.csv`.
5. Compares the tuned models on the validation partition and selects the lowest MSE.
6. Refits the selected model on train + validation and evaluates it **once** on the test partition.
7. Saves `artifacts/model.joblib` (featurizer + model), `artifacts/report.json` and the figures in `static/img/crisp/`.

All random seeds are fixed (42), so the same data gives the same results.

`monitor.py` replays May – June 2017 as if the counts arrived day by day and injects a synthetic +30% increase at
junction 1 from 2017-06-10. It writes `logs/monitoring_test.jsonl` (every record has `"simulated": true`),
`artifacts/monitoring.json` and `static/img/crisp/monitoring_test.png`.

The agent evaluation in `artifacts/control_evaluation.json` comes from training the DQN 5 times (60 episodes each)
from the Dashboard / `POST /api/train_control` and averaging the comparison with the fixed-time signal.

## Information system (Activity R3A3)

The Flask application is a web information system that manages one business process with the forecast model inside it:

```
forecast (ML)  ->  timing plan (draft)  ->  submitted  ->  approved / rejected (administrator)  ->  applied
                                                                      real outcome recorded  ->  error measured
```

* **Forecast**: an operator chooses an intersection, date and hour; the server runs the saved model
  (`artifacts/model.joblib`: featurizer + Gradient Boosting) and stores the result with the user, date, input,
  output, model version and response time (`inferences` table).
* **Timing plan**: the forecast proposes a green time between 8 and 60 s (`services/plan_rules.py`, the same limits as
  the simulator). The operator adjusts it, an administrator approves or rejects it, and an approved plan is marked as applied.
* **Outcomes**: when the real count is known it is saved in the forecast; the absolute error feeds the reports and the
  monitoring alerts.
* **Incidents and feedback**, **intersection catalogue**, **reports**, **monitoring** and **user management** complete the system.

### Roles

| Role | Can do |
|---|---|
| Viewer (default for new accounts) | Read intersections, approved/applied plans and reports; send feedback |
| Operator | Everything a viewer can, plus run forecasts, create/edit/submit its own plans, mark approved plans as applied, record outcomes, report incidents |
| Administrator | Everything, plus approve/reject plans, manage intersections and users, see all forecasts and incidents, monitoring |

Roles are enforced on the server (`controllers/auth_controller.py`: `login_required`, `roles_required`). Users register
themselves as viewers; the role field is never read from the registration form, only an administrator can change it,
nobody can change their own role, and one active administrator always remains. Passwords are stored with scrypt hashes
(Werkzeug); forms carry a CSRF token; 5 wrong passwords lock the account for 15 minutes.

### Database

`models/database.py` creates the schema at start-up (`users`, `intersections`, `model_versions`, `inferences`,
`timing_plans`, `incidents`, `app_logs`).

* Default: SQLite file `data/app.db` (no installation needed). Change the location with `DATABASE_PATH`.
* PostgreSQL: set `DATABASE_URL=postgresql://user:password@host:5432/dbname`. Use it in production: the file system of a
  free Render instance is erased on every deploy, so SQLite data would not persist there.

At the first start the intersections are loaded from `data/raw/Intersecciones_Chia.csv`, the model version is registered
and the accounts are created from environment variables (see `.env.example`; no secret is stored in the repository):

| Variable | Purpose |
|---|---|
| `SECRET_KEY` | signs the session cookies (required in production) |
| `DATABASE_URL` / `DATABASE_PATH` | PostgreSQL URL, or SQLite file location |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_EMAIL` | first administrator |
| `TEST_USERS_PASSWORD` | creates `admin_test`, `operator_test` and `viewer_test` with that password |
| `ERICK_PASSWORD`, `SANTIAGO_PASSWORD`, `IVAN_PASSWORD`, `EDWARD_PASSWORD` | password of `<name>_operator` and `<name>_viewer`; if empty, a default stored only as a hash in `services/seed.py` is used (the passwords are given privately to the instructor) |
| `SESSION_COOKIE_SECURE` | `1` to send the cookie only over HTTPS |

### Forecast API

The API uses the session of a logged-in operator or administrator (the same permissions as the web page).

```bash
curl -c cookies.txt -X POST http://localhost:5000/login -H "Content-Type: application/json" \\
     -d '{"username": "operator_test", "password": "Test12345"}'
curl -X POST http://localhost:5000/v1/forecast -b cookies.txt -H "Content-Type: application/json" \
     -d '{"date": "2017-06-12", "hour": 8, "intersection_id": 1}'
```

| Field | Type | Description |
|---|---|---|
| `date` + `hour`, or `datetime` | input | `YYYY-MM-DD`, 0-23, or `YYYY-MM-DD HH:00` |
| `intersection_id` (or `junction`) | input | catalogue id (or junction 1-4) |
| `vehicles_per_hour` | output | forecast |
| `group` | output | Off-peak, Moderate or Peak |
| `hourly_curve` | output | forecast for the 24 hours of that day |
| `model`, `model_version`, `inference_id` | output | selected model, artifact version and the saved history record |

`GET /v1/monitoring` (administrators) returns the monitoring checks as JSON. Forecasts and errors are also appended to `logs/*.jsonl`.

## Tests

```bash
pip install pytest
python -m pytest tests -q
```

The tests (`tests/test_system.py`) use a temporary database and check registration, login, lock-out, CSRF, the
permission of every role, intersection CRUD with validation, the full plan workflow, the saved model against the
training pipeline, outcome recording, logging and data persistence after a restart. If PyTorch is not installed,
`tests/torch_stub.py` replaces it, because the saved model is a scikit-learn model.

## Deploy on Render

`render.yaml` creates the web service and a PostgreSQL database (`smart-traffic-db`) and connects them through
`DATABASE_URL`. After the first deploy open the service in the Render dashboard and set the secrets
`ADMIN_USERNAME`, `ADMIN_PASSWORD` and `TEST_USERS_PASSWORD`; `SECRET_KEY` is generated automatically. The service
checks `/health`. The saved model is loaded at start-up, so no training is needed on the server. Check the current
limits of the free plans (the free instance sleeps after inactivity and free databases can expire).

## Data note

The hourly counts come from a public traffic dataset and are assigned to four intersections of Chía as a case study;
they are not field measurements from Chía.
